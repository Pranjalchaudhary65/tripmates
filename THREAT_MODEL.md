# TripMates — THREAT_MODEL.md

STRIDE-lite analysis. For each category: the specific threats that matter
for a "trust strangers to travel with" app (not a generic checklist), the
mitigation, and where it lives in code/schema. This file is read alongside
`DESIGN.md` and the README's OWASP Top 10 checklist — this file asks "what
can go wrong", the README checklist confirms "here's proof we covered it".

Trust boundaries in this system:
- Browser ↔ API (untrusted input, the biggest boundary)
- API ↔ Postgres (assume SQL only via parameterized JPA/JPQL, never trusted beyond that)
- API ↔ Redis (session/refresh-token state, assume network between them could be sniffed inside the Docker network — still TLS in prod)
- API ↔ Object storage (verification selfies, profile/meetup photos — never served directly to the browser)
- API ↔ pluggable AI adapter (treated as untrusted output generator — never executes anything, never gets secrets, output is always sanitized before storage/display)
- Mobile/web client ↔ WebSocket (same auth boundary as REST, often forgotten)

## S — Spoofing

| Threat | Mitigation | Where |
|---|---|---|
| Attacker brute-forces/guesses passwords | Argon2id hashing (tuned cost), breached-password check via k-anonymity range query against HaveIBeenPwned-style API, per-IP + per-email rate limiting (Bucket4j in Redis), CAPTCHA after 3 failures, exponential-backoff lockout after 5 (1 min doubling to 15 min). Attempts are charged before the password check in one atomic Lua script, so parallel guesses cannot get past the count | `identity.service.PasswordHashingConfig`, `identity.password.HibpBreachedPasswordChecker`, `identity.service.PasswordPolicy`, `identity.service.LoginService`, `identity.service.LoginLockout`, `identity.captcha.CaptchaVerifier`, `platform.ratelimit.RateLimiter` |
| Attacker uses the lockout to lock a victim out by failing on purpose | Lockout is temporary and capped at 15 minutes, and attempts refused while locked do not extend it. A browser holding a device cookie that has already signed in to the account successfully gets its own counter, so failures from anywhere else never lock the owner's own browser. A made-up cookie value has no matching success in `login_history` and stays on the shared counter | `identity.service.LoginService`, `identity.controller.DeviceCookie`, `DESIGN.md` §1 Login |
| Someone signs in with a stolen password and the owner never notices | A successful login from a browser whose device hash has no earlier success for that account emails the owner (time and IP). The alert leaves out the User-Agent, since the person signing in chose it and could use it to put their own text into the victim's inbox | `identity.service.LoginService`, `identity.mail.IdentityMailer` |
| Client forges `X-Forwarded-For` to escape per-IP limits or to frame another IP in `login_history` | Only Tomcat's RemoteIpValve reads the header. It trusts it only when the socket peer is in `TRUSTED_PROXIES` (empty by default, meaning trust no one), and reads it from the right, where our own proxy's entries sit; entries the client writes on the left are never used. IP literals only: nothing is DNS-resolved | `application.yml` `server.tomcat.remoteip`, `platform.web.ClientAddress` |
| Stolen/replayed refresh token used to impersonate a user indefinitely | Refresh token **rotation with reuse detection**: each refresh replaces the token, and presenting a replaced one revokes the entire family, its access tokens included, forcing re-login on every device in that family. Rotation is one atomic Redis Lua script, so parallel refreshes can never leave two live tokens. The one exception is the token replaced less than 10 s ago, which buys an access token but no new refresh token, so two tabs racing do not sign a real user out; any later use is theft. Tokens stored only as SHA-256; families expire 30 days after sign-in whatever happens | `identity.service.RefreshTokenStore`, `identity.service.SessionService`, `refresh_token_families` table |
| Stolen access token (XSS, a log, a shared screenshot) keeps working after the user signs out or the theft is noticed | Every authenticated request checks that the token's session (`sid`) still exists in Redis, so logout, "revoke all devices" and reuse detection kill outstanding access tokens immediately, not after their 15 minutes. The access token lives only in page memory; the refresh token is in an HttpOnly cookie no script can read | `identity.token.SessionLivenessFilter`, `identity.controller.RefreshCookie` |
| Attacker fakes a trusted identity using someone else's photos | Tiered verification is explicitly a *confidence score*, not a boolean "verified" — selfie match tier compares the submitted selfie against `users.profile_photo_key` (mock `LivenessVerifier` in dev, pluggable commercial liveness/face-match provider in prod); trust score formula weights SELFIE_MATCH far higher than EMAIL-only, so the UI and matching never treat all "verified" users as equivalent. No government ID is involved at any tier — see `DESIGN.md` → "No government ID verification" for why, and note that this is a deliberately weaker assurance than a document check, compensated by the Public Meet-up Protocol | `identity.verification.LivenessVerifier`, `identity.service.SelfieVerificationService`, `DESIGN.md` Trust Score spec |
| Face-spoofing — a photo-of-a-photo, a video replay, or a deepfake is presented to pass selfie verification | The `LivenessVerifier` interface requires a liveness signal (e.g. an in-app challenge like a prompted head-turn or blink, or a short live capture), not just a static image match — a still photo alone cannot satisfy it. Mock implementation simulates the liveness check in dev; the commercial provider swapped in later is where this actually gets hard to fool. The prompt is chosen by the server when the check starts, and the check is single-use, bound to the account and expires in 2 minutes, so frames recorded in advance are unlikely to show the right movement in time. The mock provider only refuses two identical frames | `identity.verification.LivenessVerifier`, `identity.verification.SelfieChallenges` |
| CSRF — a malicious page submits a cookie-authenticated request on behalf of a logged-in user | Access token is a bearer token the SPA attaches explicitly (not auto-sent); only the refresh token lives in a cookie, `HttpOnly + Secure + SameSite=Strict` and path-scoped to `/api/v1/auth/refresh`, the one endpoint that reads it. That endpoint also requires the custom header `X-TripMates-CSRF: 1`, which no cross-origin page can send without passing a CORS preflight, and the CORS filter rejects any other origin outright. A double-submit token was the first plan; it needs a cookie scripts can read on the app's origin, which a separate API host cannot set without widening it to the parent domain, so the custom header replaced it | `platform.security.CsrfHeaderFilter`, `platform.security.ApiCorsFilter`, `identity.controller.RefreshCookie` |
| WebSocket connection impersonates another user, or listens in on someone else's conversation | The access token goes in the STOMP `CONNECT` frame (a browser cannot set headers on the handshake) and through the same decoder, session-liveness and active-account checks as HTTP. After that the socket can subscribe to exactly one destination, `/user/queue/chat`, which Spring resolves to that connection's own private queue; `/topic/...`, raw `/queue/...` names and another user's `/user/{id}/...` are refused and the socket closed. Which conversations reach a queue is decided by the server at push time from the two user IDs on the conversation row, never by anything the client subscribes to. A refused frame gets an ERROR saying only "Not allowed" | `chat.websocket.StompAuthChannelInterceptor`, `chat.websocket.ChatPush`, `chat.websocket.ChatStompErrorHandler`, `ChatSocketIntegrationTest` |
| A socket stays open after its session is revoked (sign-out, "revoke all devices", detected token theft) and keeps receiving messages | Every 30 s each open socket is checked: closed once its access token has expired or its session no longer exists in Redis, and closed too if Redis cannot be asked (fail closed). A socket that never authenticates is closed after 10 s | `chat.websocket.ChatConnections`, `ChatSocketIntegrationTest` |
| Cross-site WebSocket hijacking: a malicious page opens a socket to the API from the victim's browser | The handshake is refused for any `Origin` outside the CORS allowlist (both by the CORS filter and by the endpoint itself), and no cookie authenticates a socket anyway: without the access token, which lives only in the SPA's memory, CONNECT is refused | `chat.websocket.ChatWebSocketConfig`, `platform.security.ApiCorsFilter` |
| User misrepresents their age at signup to access a platform whose purpose is introducing them to adult strangers | `date_of_birth` has a DB-level `CHECK` (≥18 years ago) that a direct API call can't bypass, not just a signup-form validation; service layer duplicates it for a clear rejection message | `DESIGN.md` §1 `users` (`ck_users_adult`), `identity.service.AgePolicy`, `identity.service.RegistrationService` |
| Pre-registration hijack — attacker registers a victim's email with their own password, then the victim types the code they receive and verifies the attacker's account | Verifying needs the emailed code **and** the `verificationId` returned only to the client that set the current password; re-registering an unverified address replaces its credentials and supersedes the old code, and resend only works with the newest id. So a victim can only ever verify the registration they made | `identity.service.OtpService`, `identity.service.RegistrationService` |
| Stolen password used to sign in to an account that has 2FA | A correct password opens no session: the response is only a challenge (256 random bits, stored hashed in Redis, 5 minutes on the application clock), with no access token, no refresh cookie and no device cookie. A challenge takes 5 codes, charged atomically in Lua before each is checked, then the password is needed again. Codes also count against a lockout counter of their own (`{password counter}:second-factor`, same 5-failure doubling lock as passwords) that a new challenge does not reset, plus a per-IP bucket on the route. Every wrong code writes a `BAD_SECOND_FACTOR` row to `login_history` | `identity.service.SecondFactorLoginService`, `identity.service.SecondFactorChallenges` |
| A TOTP code seen over a shoulder or relayed by a phishing proxy is replayed inside its ±30-second window | A code is accepted only for a time step later than `users.totp_last_used_step`, which is updated in the same transaction under the user row lock, so a code works once and an older code never works after a newer one. The confirming code at enrolment counts as used. Proven concurrently: the same code raced on two logins opens exactly one session. Every step in the window is compared in constant time, whichever matches | `identity.service.SecondFactorVerifier`, `identity.service.Totp` |
| A stolen access token (or a session left open on a shared computer) is used to switch 2FA off, bind the attacker's own authenticator app, or mint fresh backup codes | Setup needs the password; disable and regenerate need the password **and** a current TOTP or unused backup code; setup is refused while 2FA is on, so a live secret can never be replaced. All four routes share a 10-per-15-minutes bucket per account, so they are no guessing oracle. A wrong password or code answers `400 reauthentication_failed` either way. Turning 2FA on or off ends every other session (`SECURITY_CHANGE`). Enabling, disabling, regenerating and signing in with a backup code each email the owner, without ever including a code or the secret | `identity.service.TwoFactorService`, `identity.mail.IdentityMailer` |
| Backup codes read from a leaked `totp_backup_codes` table, or one used twice | Ten codes of 50 random bits each, stored only as HMAC-SHA256 under the server key (prefixed and bound to the user ID), shown once. A code is marked used under the user row lock; regenerating deletes the old set in the same transaction as the new one is inserted, and disabling 2FA deletes it | `identity.service.BackupCodeHasher`, `identity.service.SecondFactorVerifier` |
| Badge laundering: match a selfie against your own photo, then swap in someone else's photo and keep the SELFIE_MATCH tier | Replacing the profile photo drops a SELFIE_MATCH account to PHONE and withdraws a selfie waiting for review, in the same transaction; the tier comes back only when a new selfie matches the new photo. `ck_users_tier_evidence` refuses SELFIE_MATCH on a row with no photo at all | `identity.service.ProfilePhotoService`, `identity.entity.User#replaceProfilePhoto` |
| The selfie matcher used as an oracle: submit borrowed photos, adjusting each one, until one scores high enough | The similarity score is never returned to the user, only APPROVED, REJECTED or PENDING; five submissions per account per day; each needs a fresh server-chosen challenge | `identity.service.SelfieVerificationService`, `VerificationLimitProperties` |
| An admin approves their own flagged selfie | The service refuses a reviewer deciding their own verification (403), and `ck_idverif_reviewer_not_self` refuses the row even if that check were skipped | `identity.service.AdminVerificationService` |
| A ring of fake accounts launders trust by vouching for each other | Only a SELFIE_MATCH account can vouch, at most 5 active vouches each, counted under the voucher's row lock so parallel requests cannot pass the cap; a vouched account that is later suspended costs every active voucher a `VOUCH_PENALIZED` event | `identity.service.VouchService` |
| Verification code guessed (1 in 10^6) or read from a leaked `otp_codes` table | 5 attempts per code, counted under a row lock so parallel guesses cannot exceed it, 10-minute expiry, 5 codes per account per day; codes stored only as HMAC-SHA256 under a server-side key, so the table alone is useless | `identity.service.OtpService`, `identity.service.OtpCodeHasher` |

## T — Tampering

| Threat | Mitigation | Where |
|---|---|---|
| Client sends a manipulated settlement/expense `amount` | The only amount a client states is the expense it paid for itself: whole paise, read as an exact decimal (so `1250.5` is refused rather than truncated), 1 paisa to ₹10 lakh, with exact shares that must add up to it exactly. The payer is always the caller, never a field. Every settlement amount is computed by the server (debt simplification over the ledger) and a payment request names only a settlement ID. The database refuses any ledger transaction whose legs do not balance or do not equal its stated amount (deferred constraint trigger) | `settlement.controller.LedgerController`, `settlement.service.LedgerService`, `settlement.service.ExpenseSplit`, `V18__create_settlement_ledger.sql` |
| Two concurrent requests overfill a trip slot, or double-write a settlement confirmation | Optimistic locking (`@Version`) on `trips` and `settlements`. Every write to one trip's ledger first takes that trip's `trip_ledgers` row lock, and a settlement can reach the ledger only once (`ledger_transactions.settlement_id` is UNIQUE). Proven by racing 8 confirms of one payment (exactly one ledger pair) and 12 expense adds (every one recorded, balances and plan exact), and a stale `@Version` write is shown to be refused. A user's history is always `SUM(ledger_entries)`, never a column two writers can race on | `settlement.service.LedgerService`, `SettlementConcurrencyIntegrationTest` |
| Attacker edits historical audit/ledger/transition rows directly (DB access, insider, bug) | `ledger_entries`, `ledger_transactions`, `settlement_state_transitions` and `settlement_overdue_notices` refuse UPDATE, DELETE and TRUNCATE through a trigger that fires for every role, the owner included (the app currently connects as the owner, which a REVOKE cannot restrict; the REVOKE is in place for when it connects as a separate role). Their repositories expose only insert and read, and their entities are `@Immutable`. Corrections are reversing transactions. `audit_log` is additionally hash-chained so even a privileged edit breaks `row_hash` continuity, caught by a scheduled integrity sweep | `V18__create_settlement_ledger.sql`, `settlement.repository.*`, `LedgerIntegrityIntegrationTest` |
| One side alone moves the ledger: a payer marks their own payment confirmed, or a payee confirms a payment nobody said they sent | Only the payee's confirm writes the ledger, and only from MARKED_PAID; the payer calling confirm is refused (`cannot_confirm_own_payment`) whatever the state, and a confirm on PROPOSED is refused (`not_marked_paid`). Both are tested to write zero ledger rows. Every state change is an append-only `settlement_state_transitions` row with its actor | `settlement.service.LedgerService#confirm`, `settlement.entity.Settlement`, `SettlementIntegrationTest` |
| A payment link is altered to pay someone else: a payee name crafted as `Asha&pa=thief@bank`, or a UPI ID that breaks out of the link | A UPI ID is accepted only as `name@bank` from a fixed character set (letters, digits, `.`, `_`, `-`), lower-cased; the name is percent-encoded; the link is built by the server for the payer only. A UPI ID changed in the last 48 hours is flagged to the payer, and the payer's own UPI app shows the account holder's name before anything is sent | `identity.service.UpiIdService`, `settlement.service.UpiLinks`, `UpiLinksTest` |
| A user games the safety carve-out — marks ordinary (`CONVENIENCE`) cancellations as `SAFETY` to dodge the `GHOST` trust-score penalty | No individual `SAFETY` cancellation is ever penalized (that would defeat the point of the carve-out), but every one auto-files a `blocks_reports` row against the *counterparty*; a pattern of many `SAFETY` cancellations from the same user, each naming a different counterparty, surfaces through the same report-volume signal the moderation queue already uses for harassment — reviewed by a moderator, never auto-penalized on the canceller's trust score speculatively | `trust.TrustScoreService`, `platform.ModerationService`, `DESIGN.md` §Trust Score Engine → Safety carve-out |
| A client sends its own idea of what a quiz answer means (a score, a dimension) to steer its vibe profile or someone's match | The questions, options and their scoring numbers live only on the server; a request carries option IDs, each checked against its own question, and the profile is computed from them server-side. Option numbers are never sent to the client | `vibe.service.VibeQuiz`, `vibe.service.VibeService` |
| A host fills a trip past its slots by accepting many requests at once, or a request is both accepted and rejected | Accepting goes through `Trip.claimSlot` under the trip's `@Version`; of two claims that read the same version only one commits, and the loser retries from a fresh read and answers `trip_full` once nothing is left. `trip_members.version` does the same for the request. `ck_trips_filled_slots` and the OPEN/FULL CHECKs refuse an overfilled row even if the code were wrong. Proven by racing 8 parallel accepts at 1 slot, at the last slot of a part-filled trip, and at 3 slots | `trips.service.JoinRequestService`, `trips.entity.Trip`, `SlotClaimConcurrencyIntegrationTest` |
| A join request accepted or rejected by someone who is not the trip's host (the requester accepting themselves, a stranger guessing request IDs) | A decision names the request alone and is refused with 404 unless the caller hosts its trip, the same answer as an unknown ID; the requester cannot accept their own request either | `trips.service.JoinRequestService`, `EndpointAuthorizationMatrixIntegrationTest` |
| A traveller gets round a host's deal-breaker (a same-gender trip, a trust minimum) by opening the trip through a shared link instead of browse | Deal-breakers are checked in SQL on both sides for browse (where a ruled-out trip is never listed) and again when a join request is made (`409 deal_breaker_conflict`, no row written). Both read the same SQL fragments, so they cannot drift apart. Gender comes from the server's own record, and someone who prefers not to say it cannot meet a SAME preference, since it cannot be checked | `trips.repository.DealBreakerRules`, `trips.service.JoinRequestService`, `MatchIntegrationTest` |
| A stale or tampered cached match score is shown after a profile changes | A cached row is served only while its scorer id and both profile `updated_at` stamps equal the current ones; otherwise it is recomputed and replaced. A row whose explanation does not read back is recomputed, never shown. Deal-breakers are never cached | `trips.service.MatchService`, `trips.repository.MatchCacheRepository` |
| Mass-assignment — client sends extra JSON fields (`role: "ADMIN"`, `trustScore: 100`) that get bound onto an entity | Every endpoint binds to a dedicated request DTO with Bean Validation, never a JPA entity directly; MapStruct maps DTO → entity explicitly field-by-field, so an unmapped field is simply dropped, not silently persisted | All `*.dto.*Request` classes, MapStruct mappers |
| Tampered JWT (algorithm confusion, modified claims) | HS256 with a server-held key of at least 256 bits from the environment, no default. The verifier offers a key only for `alg: HS256` and only for the exact `kid` it was derived for, so `none`, HS384/512, an RS256 header and an unknown or missing `kid` all fail; `typ` must be `at+jwt`, and `iss`, `aud`, `exp`, `iat`, `sub`, `sid`, `jti` and `role` are all required. The 15-minute expiry limits the damage window of a key compromise; replacing the key without keeping it as "previous" invalidates every token it signed at once | `identity.token.AccessTokenDecoderConfig`, `identity.token.AccessTokenIssuer`, `identity.token.AccessTokenKeys` |

## R — Repudiation

| Threat | Mitigation | Where |
|---|---|---|
| User denies marking a settlement paid/confirmed, or disputes it after the fact / admin denies suspending an account | `audit_log` hash chain records every auth event, safety event, settlement confirmation, and admin action with `actor_user_id`, timestamp, and IP, in the same transaction as the change — not best-effort logging after the fact | `platform.AuditLogService`, `DESIGN.md` §9 |
| User claims "I never saw that review" / "I didn't ghost, that was a safety cancellation" | `settlement_state_transitions` and `trust_score_snapshots` keep a full timestamped history independent of current row state; `trip_members.cancellation_type`/`cancellation_reason` are recorded at cancellation time, not reconstructed later, so any score or settlement dispute can be reconstructed exactly as it happened | `DESIGN.md` §Settlement flow & state machine, §Trust Score spec |
| "The AI said something inappropriate, not me" (icebreaker/moderation messages) | Generated text never becomes a message on its own: icebreakers are suggestions shown only to the asker, cleaned and redacted like a message (a suggestion that would carry contact details is dropped), and become a message only when that person sends it as their own words. SYSTEM messages have `sender_id = NULL`, `kind = 'SYSTEM'` and a fixed code instead of text, enforced by `ck_chat_messages_shape`. Messages have no edit or delete, so neither person can rewrite what they said after it was read | `chat.service.ConversationService#icebreakers`, `chat.entity.ChatMessage`, `V13__create_chat.sql` |

## I — Information Disclosure

| Threat | Mitigation | Where |
|---|---|---|
| IDOR — user requests `/api/trips/{id}/settlements` or `/api/users/{id}/reviews` for an ID that isn't theirs | Deny-by-default in the filter chain plus an explicit ownership check inside the service (never trust the URL path alone). A non-owner gets **404**, the same answer as for an ID that does not exist, so an ID never confirms it is in use. Routes that act on the caller's own account take no user ID at all. **Every** mapped route is listed with its access rule in one matrix test that calls it as anonymous, as a non-owner and as the owner; a coverage test reads the routes from Spring MVC and fails the build when one has no entry | `platform.security.EndpointAuthorizationMatrixIntegrationTest` |
| TOTP secret read from a DB dump or backup | AES-256-GCM under the user's data key, which is stored only wrapped by a KEK from `DATA_ENCRYPTION_KEK` (no default). Additional data binds each ciphertext to its user and column, so a value copied to another row does not open. The secret is returned once, by setup, and by no endpoint after; crypto-shredding the data key makes it unreadable for good | `identity.crypto.FieldEncryption`, `identity.crypto.KeyEncryptionKey` |
| Phone number, emergency contact, precise location leak via a DB dump, log file, or API response | Field-level AES-GCM envelope encryption at rest for these fields; blind-index (HMAC) column for the one field (`phone`) that must stay searchable; PII masked before any log statement, correlation IDs used instead of raw identifiers in logs | `DESIGN.md` §1 `users`, §7 `itinerary_shares`/`checkins`, `platform.logging.PiiMaskingConverter` |
| A photo upload leaks a user's home address via embedded EXIF GPS metadata | Every uploaded image is re-encoded through a library that strips all EXIF/metadata before storage; original bytes are never persisted: decoded with metadata ignored and written out as a new JPEG, so EXIF, ICC profiles, comments and bytes appended after the image (a polyglot payload) are all dropped. A test uploads a JPEG with a GPS-bearing EXIF segment and checks the stored bytes | `identity.upload.ImageSanitizer` |
| Verification selfie image served from a predictable/public URL, or retained longer than its purpose requires | Files are stored outside the web root under randomized (UUID) names; the only access path is a short-lived signed URL issued per-request to an authorized viewer (the user themselves or an admin reviewer). On top of that, a hard retention window (default 7 days) applies regardless of outcome — a scheduled job purges `selfie_image_key` once `purge_due_at` passes, and a test asserts no image key survives past that window in a terminal state | `identity.upload.SignedMediaUrls`, `identity.controller.MediaController`, `identity.verification.SelfiePurgeJob`, `DESIGN.md` §1 `identity_verifications` |
| User enumeration via login/register/forgot-password responses or timing | Identical response body and (approximately) constant response time whether or not the email exists, for register/login/forgot-password; actual password check always runs (against a dummy hash) even when the email doesn't exist, so timing doesn't leak existence | `identity.service.RegistrationService` (register: every rejectable check runs before the email lookup; taken addresses get a decoy `verificationId` and the owner a notice email, sent async after commit so SMTP timing does not leak), `identity.service.LoginService` (login: unknown email, wrong password, unverified, disabled and locked give one identical 401, and each runs exactly one Argon2id check, against a dummy hash for an unknown email; rate limits, CAPTCHA and lockout are keyed on the typed email, so they behave the same for addresses with no account) |
| A User-Agent crafted at sign-in (markup, a fake "security notice", terminal escapes) is shown back to the victim on the sessions screen, or to an admin | The raw header is stored (truncated to 512 chars) for audit only and never returned. The sessions list shows a device label built from a fixed list of browser and OS names, so the most a forged header can do is pick which fixed name appears; the IP and times beside it are server-observed. IDs come only from the verified token, so the list can only ever show the caller's own sessions | `identity.service.DeviceLabels`, `identity.dto.ActiveSessionMapper`, `identity.controller.SessionController` |
| Phone number enumeration: try numbers on the phone route to learn which ones have accounts | A code is sent to any well-formed number and the answer is the same 202 for all of them; "verified on another account" is said only after the caller has entered the right code, proving they hold that phone already | `identity.service.PhoneVerificationService` |
| A leaked `users` table maps blind indexes back to phone numbers by hashing every mobile number | The index is HMAC-SHA256 under `PHONE_BLIND_INDEX_KEY`, a key kept in the environment and separate from the OTP key, so the table alone gives nothing to compare against; the number itself is AES-GCM under the user's data key | `identity.phone.PhoneBlindIndex`, `identity.crypto.FieldEncryption` |
| A vouch or other resource withdrawn through someone else's ID (IDOR) | A vouch is found by ID and voucher together; any other caller gets the same 404 as for an ID that does not exist. The authorization matrix checks this rule (OWNED) for the route | `identity.service.VouchService`, `EndpointAuthorizationMatrixIntegrationTest` |
| A stored image reached through a crafted object key (`../`, an absolute path) | Keys are generated server-side as a prefix and a random UUID; storage refuses any key not matching that pattern and any resolved path outside its root. A media link names a key only inside an HMAC-signed token | `identity.upload.LocalDiskObjectStorage`, `identity.upload.MediaKind` |
| Someone else's vibe profile, quiz answers or deal-breakers read through the API (they reveal habits, gender preference and the trust bar a user sets) | Every vibe route acts on the caller's own account and takes no user ID, so there is nothing to swap; the raw answers are never returned, even to their owner. Matching will expose only its explanation, never the other side's profile | `vibe.controller.VibeController`, `EndpointAuthorizationMatrixIntegrationTest` |
| A trip, a join request or a host's identity read by someone with no business seeing it (a cancelled trip's plan, who asked to join whom, the host's account ID) | A trip is visible to its host, to people with a request on it, and, while OPEN or FULL with an active host, to signed-in users; otherwise 404 like an unknown ID. Inboxes act on the caller's own account; a `tripId` filter only narrows the caller's own trips. Other people appear as a first name and a verification tier, read from the `user_public_facts` view, which has no email, phone, surname, date of birth or photo key; no trip response carries another user's ID | `trips.service.TripService`, `trips.repository.TripQueries`, `V8__create_user_public_facts.sql` |
| A suspended or banned host keeps collecting requests, or a suspended requester gets accepted | Browse, detail and join leave out trips whose host is no longer active; accepting refuses a requester who is no longer active (404), and the host's inbox drops them | `trips.repository.TripQueries`, `trips.service.JoinRequestService` |
| The match explanation used to read another user's vibe profile or deal-breakers | The explanation is fixed sentences about dimensions that clearly agree or clearly differ, never raw values, numbers or the quiz answers; middling dimensions are left out. A blocked match names only the rule ("The host is travelling only with people of their own gender."), not the host's settings beyond it. The host's ID never leaves the service layer, and profiles reach trips only through `MatchProfiles`, which no endpoint exposes | `trips.service.RuleBasedMatchScorer`, `trips.service.MatchService`, `vibe.service.MatchProfiles` |
| Masked chat accidentally reveals real contact details before trip lock | Redaction runs server-side on every message *before* it is stored (not a display-time filter that could be bypassed by calling the API directly): emails, UPI IDs, links, messenger links, @handles and any run of 10+ digits become `[contact hidden]`, and the message is marked `redacted` so the sender knows. | A stranger, or someone who never finished the trip, posts a review; or reviews are edited or deleted afterwards | Only travellers still on the trip, in its window, one per pair (`uq_reviews_pair`); a trigger refuses edits and deletes | `ReviewService`, `V21__create_trust_score.sql` |
| A redelivered or replayed outbox event counts twice against someone | `trust_score_events.source_event_id` is UNIQUE; inserts are `ON CONFLICT DO NOTHING` | `TrustQueries.recordEvent` |
| Score history or delivered events are rewritten to hide what happened | Snapshots and trust events are append-only by trigger; outbox events can only be marked delivered or dead, once, never changed | `V20__guard_outbox_events.sql`, `V21__create_trust_score.sql` |
| One poison outbox event stops every later event from being delivered | The relay skips an event that failed in the same run, counts failures in a separate transaction and sets it aside as dead after `max-attempts` | `platform.outbox.OutboxRelay`, `OutboxRelayIntegrationTest` |
| Block or report used to probe which accounts exist, or aimed at a stranger | Only someone the caller was matched or travelled with; anything else is the 404 of an unknown match | `trips.service.TripContacts`, `ModerationIntegrationTest` |
| Brigading: a few accounts report someone to get them suspended | Needs 3 different reporters in 30 days, each with first-hand trip contact (an accepted match or a shared trip), one open report each; suspension is reviewable by a moderator, never a ban; the reporter is never told the outcome | `ModerationService`, `uq_reports_open_pair` |
| Simultaneous reports each count one short and nobody is suspended, or vouchers are penalised twice | Reports about one account are counted under its row lock; `User.suspend` is a no-op on an inactive account, so the penalty runs once | `ModerationService.report`, `AccountModeration.suspend` |
| A suspended account keeps acting on live tokens | Suspension revokes every session in the same transaction; an access token dies with its session | `AccountModeration.suspend`, `SessionService.revokeEverySession` |
| A blocked person keeps reaching the blocker | Browse, trip detail, join requests and chat sends all check `user_block_facts` in both directions | `TripQueries`, `TripService`, `JoinRequestService`, `MessageService` |
| A tampered or buggy response shows a score its breakdown does not explain, or a review the double-blind should still hide | The client's strict reader refuses a breakdown whose points are not value × weight or do not add up to the score, a deduction type the formula does not have, and any review of the user shown while the user's own is still hidden; the screen then shows a generic error | `frontend/src/api/trustApi.ts`, `trustApi.test.ts` |
| A report or block sent by mistake | Folded away until asked for; block needs a confirm step, report needs a chosen reason; neither reveals anything about the other person's outcome | `frontend/src/components/ReportBlock.tsx`, `trustPages.test.tsx` |
| Report details read by anyone with database access | Sealed under the reporter's data key, bound to the report ID | `EncryptedField.REPORT_DETAILS`, `ModerationService` |
## Compliance, audit and administration

| Threat | Mitigation | Where |
|---|---|---|
| An insider or attacker with database access edits or deletes audit history | Append-only trigger for every role; each row hashed over the previous row's hash, filled by a trigger under an advisory lock; a daily check recomputes every hash in Java and records and logs the first break | `V23__create_compliance.sql`, `platform.audit.AuditIntegrity`, `ComplianceIntegrationTest` |
| The audit log keeps personal data after the person deletes their account | Metadata accepts only IDs, codes and numbers (`AuditLog` refuses anything else); no IP, name or email columns | `platform.audit.AuditLog` |
| A stolen session deletes someone's account | Deletion needs the account password again, the same refusal for any wrong password | `AccountDeletion.requirePassword` |
| Deleted data survives in encrypted columns or exports | Every data key is shredded, so every value sealed under it (messages, phone, notes, locations, report details, waiting exports) is unreadable; plaintext identifiers are scrubbed from the user row | `AccountDeletion`, `DataRequestJob` |
| Someone downloads another person's export, or an export leaks through storage links | Export is the requester's only (404 otherwise), sealed under their key in the database, never in object storage or behind a media link; cleared after 7 days; `Cache-Control: no-store` | `DataRequestService`, `DataRequestController` |
| An export reveals what the double-blind or the comfort rating must hide, or secrets | Each module exports only its own data: received reviews only once visible, rounded safety points only, no comfort rating, no password hash, TOTP secret, blind index or other people's messages | `*PersonalData` contributors |
| An email or phone number ends up in logs by accident | Every string field of every structured log line is masked; tested end to end | `PiiMaskingLogCustomizer`, `ComplianceIntegrationTest` |
| A moderator abuses their role on their own case or account | A moderator cannot decide a report they are part of (also a DB CHECK) or suspend themselves; every decision is audited; admin routes need ADMIN with a second factor, re-checked against the database | `AdminModerationService`, `ck_reports_reviewer_not_party`, `AdminGuard` |
| A racing duplicate request produces a 500 instead of the right answer | Unique-index violations are recognised from plain JDBC as well as Hibernate | `platform.error.Constraints` |
## Explicitly out of scope / accepted risk (document, don't silently skip)

- Real UPI payment initiation — settlements record a *confirmed outcome*
  and generate a `upi://` deep link, but TripMates never initiates a
  transfer itself via a PSP/UPI API. Doing so would reintroduce the
  money-movement liability that "the platform never holds money" exists
  to avoid (see `DESIGN.md`). If this becomes a funded product, that's a
  payments-provider integration triggering `SETTLEMENT_CONFIRMED` rows via
  a webhook instead of a manual confirm — not a ledger schema change.
- Real SMS/liveness providers — both are behind interfaces (`OtpSender`,
  `LivenessVerifier`) with a mock default implementation so the demo runs
  with zero API keys; a real provider is a new implementation, not a
  design change. No KYC vendor and no DigiLocker integration — those are
  document-verification flows, and this platform deliberately doesn't do
  document verification at all (see `DESIGN.md` → "No government ID
  verification"). Until real providers are configured, the PHONE tier
  (codes delivered to the email inbox by the `mailbox` sender) proves only
  what EMAIL proves, and the SELFIE_MATCH tier (the `mock` verifier compares
  images, not faces) can be passed by any two slightly different pictures
  close to the profile photo. Both log a warning at startup; neither should
  be relied on outside a demo.
- DDoS at the network layer (volumetric attacks) — out of scope for an
  application-layer threat model; would be handled by the hosting
  platform (Render/Railway) or a CDN/WAF in front of it.
