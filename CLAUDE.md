# TripMates — working protocol

Read this file in full before doing anything else in this repo. It
survives context compaction and new sessions — treat it as binding, not
as a suggestion.

## What this project is

TripMates is a trust and accountability layer for travelling with
strangers, not a "travel buddy finder". Matching is the easy part; the
project exists to solve (1) fake people, (2) people who ghost after
committing, (3) no safety net during the trip. See `DESIGN.md` for the
full data model and `PLAN.md` for the ordered build checklist.

The platform never holds money — no escrow, no wallet, no custody. The
commitment in Stage 5 is reputation (trust score), not a deposit; expenses
are split via a debt-simplification ledger that records confirmed UPI
settlements after the fact. Before trip lock, the trust ladder requires a
real public meet-up (allowlisted venue, geofenced + selfie check-in) —
chat and video verification alone are not enough to let two strangers
commit to travelling together. See `DESIGN.md` for why and the full
schema.

## How to work with Pranjal — follow exactly

   Do not start the next step until Pranjal replies "next". Never dump

5. If Pranjal says "doubt: <question>", answer it fully and then return to

6. Keep code production-shaped: no TODOs left behind, no commented-out
   blocks, no "in a real app you would…". If something must be mocked (ID

## Commit style

8. No AI attribution in commits or PRs — no "Co-Authored-By", no
   "Generated with", no tool links, anywhere. `.claude/settings.json` sets
   `"includeCoAuthoredBy": false` for this reason — don't override it.
9. Write commit messages the way a developer writes about their own
   work: plain, direct, present tense. Conventional format
   (`feat`/`fix`/`chore`/`docs`/`test` + scope), 2-3 line body on what
   changed and why. No "as requested", no "per your instruction", no
   "implemented the user's design".
10. Keep commits small and focused — one logical change each. A step that
    touches config, entities, and tests is three commits, not one.
11. Code itself carries no AI watermark either — no telltale comments, no
    "Generated by" headers, nothing that reads as anything but Pranjal's
    own work.

## Frontend scope — equal priority, not an afterthought

React + Vite + TypeScript, Tailwind, Zustand, React Router, Axios with
interceptors.

Screens: signup/login, 2FA challenge, verification centre (tier progress
bar), vibe quiz (multi-step form with saved progress), trip browse +
filters, trip detail with explainable match breakdown, join request
inbox, masked chat with icebreaker suggestions, trust score profile page,
public meet-up scheduling + geofenced check-in, settle-up screen with
debt-simplified settlement list and ledger history (no wallet — this is
obligations, not custody), trip lock flow, active trip dashboard
(check-ins + SOS button), review submission, session/device management,
report & block, admin moderation panel.

Rules:
- Auth: access token in memory only (never localStorage), refresh via
  httpOnly cookie, Axios interceptor for silent refresh + retry. This is
  the locked transport decision — don't revisit it, changing it later
  means rewriting the auth module.
- Route guards by auth state AND verification tier.
- Every form validated client-side, but never trusted — server validates
  again regardless.
- Loading, error, and empty states for every screen. No raw API errors
  shown to users.
- Build the UI for each feature in the same step as its backend. Don't
  leave the frontend for the end — a demoable app at every stage, not
  just at the finish.
- DTOs are designed for a React client: one screen needs one call, not
  five. Match explainability payload, pagination envelopes, and
  aggregated profile/trust-score views are first-class response shapes.
  API paths are versioned (`/api/v1/...`).

## Stack (do not substitute without asking)

Backend: Java 21, Spring Boot (4.x, as generated by Spring Initializr —
note the project uses the renamed `spring-boot-starter-webmvc` /
`spring-boot-starter-webmvc-test` starters, not the old `-web` names),
Spring Security 6, Spring Data JPA, PostgreSQL + PostGIS, Flyway, Redis,
WebSocket (STOMP), Spring Mail, Bucket4j, MapStruct, Argon2id.
Frontend: React + Vite, TypeScript, Tailwind, Zustand, Axios, React
Router. Infra: Docker Compose, GitHub Actions, Render/Railway. Testing:
JUnit 5, Mockito, Testcontainers (real Postgres + Redis), Spring Security
Test. AI: pluggable interface with a rule-based default implementation
and an optional LLM adapter behind a config flag — the demo must work
with zero API keys.

## Engineering non-negotiables

- Flyway for every schema change. `ddl-auto` must be `validate`, never
  `update`.
- Optimistic locking (`@Version`) on trip slots and settlements, with a
  concurrent test that actually proves the race is closed.
- Testcontainers integration tests against real Postgres and Redis.
- Append-only tables (ledger, audit log, state transitions, outbox) never
  get `UPDATE`/`DELETE` — enforced at the DB grant level, not just by
  convention. See `DESIGN.md` §Append-only enforcement.
- Deny-by-default authorization. Assume every path ID is hostile — IDOR
  is the #1 risk in this app. Write an authorization test for every
  endpoint: owner allowed, non-owner denied, anonymous denied.
- Never accept or return JPA entities at the API boundary — dedicated
  validated DTOs only, mapped with MapStruct.
- Server-side amount validation on every money operation; idempotency
  keys on every money operation.
